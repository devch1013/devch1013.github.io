핸들러 선언 × 후처리 호출

두 축을 바꿔가며 코루틴이 어디서 돌고, 무엇이 깨지는지 확인해 보세요.

핸들러 선언
후처리 호출
동작

실행 위치 · 이벤트 루프 스레드 — 응답 블로킹 없음

루프가 도는 스레드 위라 get_running_loop() 이 성공한다. 태스크가 루프에 등록되고 핸들러는 즉시 반환한다.

다만 루프는 태스크를 약한 참조로만 붙든다. 반환된 태스크 객체를 아무도 들고 있지 않으면 완료 전에 GC 되어 사라질 수 있다 — fire-and-forget 이라도 참조를 어딘가 보관해야 한다.

예외

실행 위치 · 이벤트 루프 스레드

asyncio.run() 은 새 루프를 만든다. 이미 루프가 도는 스레드에서는 중첩이 불가능해 거부당한다.

RuntimeError: asyncio.run() cannot be called from a running event loop

동작

실행 위치 · 등록은 루프 스레드, 실행은 응답 전송 후 — 응답 블로킹 없음

루프 위에서도 BackgroundTasks 는 그대로 쓸 수 있다. 코루틴이면 헬퍼가 전용 루프로 완주시키고, 동기 함수면 스레드풀에서 돈다.

예외이 글의 버그

실행 위치 · anyio 워커 스레드

워커 스레드에는 도는 루프가 없다. create_task 는 루프를 만들지 않고 찾을 뿐이라 그 줄에서 즉사하고, 핸들러는 500 을 뱉는다.

띄우려던 코루틴은 태워지지도 await 되지도 못한 채 GC 되어 두 번째 경고를 남긴다. 두 줄은 별개 사건이 아니라 인과다.

RuntimeError: no running event loop RuntimeWarning: coroutine 'notify' was never awaited

동작하지만 블로킹버린 대안

실행 위치 · anyio 워커 스레드 — 응답 블로킹 있음

도는 루프가 없는 스레드라 asyncio.run() 이 새 루프를 열어 코루틴을 완주시킨다. 예외는 안 난다.

대신 알림이 끝날 때까지 핸들러가 반환하지 못해 그만큼 응답이 늦어진다. 굴러가긴 하나 fire-and-forget 이 아니다.

동작채택안

실행 위치 · 등록은 워커 스레드, 실행은 응답 전송 후 — 응답 블로킹 없음

핸들러는 등록만 하고 즉시 반환한다. 응답이 나간 뒤 헬퍼가 코루틴을 전용 루프로 완주시킨다. 블로킹 없이 후처리가 실제로 실행되는 유일한 조합이다.

단 같은 프로세스 안이라 영속성도 재시도도 없다. 반드시 완료돼야 하는 작업은 외부 큐의 몫이다.
